# GraphDraw

A WordPress block plugin with one dynamic block, `graphdraw/diagram`. Its attributes are `code`, the Mermaid source; `zoom`, `download`, `copy` and `fullscreen`, which give visitors zoom controls, download buttons, a button that copies the code and one that shows the diagram over the whole screen; `theme`, the theme the diagram is drawn in; `caption`; and `accTitle` and `accDescr`, a title and a description for assistive technology. It supports alignment (centre, wide, full) and spacing. The editor shows a live SVG preview. The server outputs the source in a `<pre>`, and the front end replaces it with an SVG rendered by the bundled Mermaid library. A setting, off by default, keeps a PNG image of each diagram of a post, which feeds and browsers that run no JavaScript get instead of the source.

The `[mermaid]` shortcode outputs the same diagrams where the block can't be used: the classic editor, page builders, text widgets. In Elementor, a widget of the plugin, Mermaid Diagram, has the block's settings and a live preview. A setting, off by default, also shows the code that is marked as Mermaid in a post, such as `<pre><code class="language-mermaid">`, as diagrams.

Supports WordPress 6.6+ and PHP 7.4+ (header of `graphdraw-mermaid-diagrams-flowcharts.php`).

## Commands

| Command | What it does |
| --- | --- |
| `npm ci && composer install` | Install dependencies, and generate Composer's autoloader in `vendor/` |
| `npm start` | Rebuild `build/` on every change |
| `npm run build` | Production build into `build/` |
| `npm run lint:js` | ESLint on `src/` |
| `npm run lint:css` | Stylelint |
| `npm run lint:php` | PHPCS: WordPress standards, PHP 7.4 compatibility, text domain |
| `composer cbf` | Auto-fix PHPCS issues |
| `npm run format` | Prettier on `src/` |
| `npm run test:unit` | Jest unit tests |
| `npm run test:php` | PHPUnit tests, on WordPress's test library. They need a MySQL database of their own: its tables are dropped. Set `WP_TESTS_DB_NAME`, `WP_TESTS_DB_USER`, `WP_TESTS_DB_PASSWORD` and `WP_TESTS_DB_HOST` (defaults: `wordpress_tests`, `root`, empty, `127.0.0.1`). The tests in `tests/Elementor/` run afterwards with Elementor active (`composer test:elementor`, `phpunit-elementor.xml.dist`); the others run as on a site without it |
| `npm run plugin-zip` | Release zip: a fresh build, the autoloader without development dependencies, and the `files` listed in `package.json` |

The pre-commit hook runs the three linters. CI (`.github/workflows/ci.yml`) runs the linters and both test suites, the PHP one on a MySQL service and again on PHP 7.4, makes the release zip, checks that it holds the build and an autoloader that loads every class, and attaches it to the run.

`build/` and `vendor/` are generated and not committed. To try a change in WordPress, run `composer install` and `npm run build`, then use any local install with this directory in `wp-content/plugins/`, or run `npx @wp-playground/cli@latest start` here.

## Layout

- `graphdraw-mermaid-diagrams-flowcharts.php`: loads Composer's autoloader and starts the plugin with `graphdraw()->init()`. Without the autoloader or the build, it shows a notice instead.
- `includes/`: the PHP classes, in the `GraphDraw` namespace, one per file named after the class, in the folder of its namespace. Composer autoloads them (PSR-4). The root holds what other code may call and what every request needs.
  - `Plugin`: lists the parts that add hooks, and adds the hooks of each on the requests that need it: every request (`PARTS`), the admin (`ADMIN_PARTS`), or once an action fires (`DEFERRED_PARTS`). `graphdraw()`, in `functions.php`, returns its one instance: `get( SomeClass::class )` returns a part, and `diagram()` and `themes()` the two that integrations call.
  - `Container`: creates the objects, one of each, when they are first asked for, with the objects their constructors ask for. `Hookable` is the interface of a part that adds hooks.
  - `Files`: the paths and the URLs of what `build/` holds, and the plugin's basename.
  - `Options`: reads the settings, each stored in an option: the site's renderer (`graphdraw_renderer`), the site's theme (`graphdraw_theme`) and the switch of each optional part. `get_renderer()` is what every request reads: the option (`get_site_renderer()`, which the settings page shows), then the `graphdraw_renderer` filter, and Mermaid.js for anything that names no renderer. `Options::ALL` lists them, and `uninstall.php` deletes them.
  - `Renderers`: the names of the renderers, `mermaid` and `pele`, and `sanitize()`, which gives Mermaid.js for a value that names neither. `Assets::LIBRARIES` has the handle of each one's library.
  - `PeleOptions`: the options a site gives Pele, from the `graphdraw_pele_options` filter, cut to the known keys of the right type. `RendererSettings` tells them, to `Assets` and `Admin\Editor`'s scripts, as `peleOptions`, only with Pele and only when there are some.
  - `IconPacks`: the icon packs a site registers, from the `graphdraw_icon_packs` filter (`name => URL of an Iconify JSON file`): a name of lower-case letters, digits and hyphens, an `http` or `https` URL through `esc_url_raw()`, the rest dropped. `RendererSettings` tells them, to `Assets` and `Admin\Editor`'s scripts, as `iconPacks`, with either renderer and only when there are some.
  - `RendererSettings`: what a script needs to build its renderer, the same for the front end and the editor: `add_to()` adds `mathUrl`, then the settings of `PeleOptions` and `IconPacks`. `Assets` and `Admin\Editor` go through it, so the front end loads it on every page with a diagram.
  - `Assets`: registers the `mermaid-js` and `graphdraw-diagram` assets from `build/`, and tells the latter, once the page's scripts are enqueued, on the front end and in the admin (a filter may pick the renderer by page), the renderer, the URLs of Mermaid's and Pele's ES module builds and of the controls, and the translated labels; the math module's URL, Pele's options and the icon packs come from `RendererSettings`.
  - `Diagram`: the diagram markup, shared by the block and other integrations. `render()` outputs a diagram from settings named as the block's attributes, for the shortcode and the Elementor widget.
  - `Themes`: the themes a diagram can be drawn in, those offered with the request's renderer (`get_offered()`) and the offered theme each other one is shown as (`get_aliases()`), the site's theme, and the one a diagram gets: its own, or else the site's.
  - `DiagramTypes`: the diagram types with starter code, the one source of the block's variations and of the `list-diagram-types` ability, and the detection of a diagram's type from its first keyword.
  - `Integrations/`: what outputs diagrams.
    - `Block`: registers the block from `build/` and renders it.
    - `Shortcode`: the `[mermaid]` shortcode, and `[graphdraw]`, the tag no other plugin takes. It reads the Mermaid source back out of what the content filters made of it, and outputs it through `Diagram`.
    - `CodeBlocks`: the code marked as Mermaid, shown to visitors as diagrams: a `<pre>` element with the `language-mermaid` class, or whose `<code>` element has it, in a Code block or in classic content. A switch on the settings page, stored in the `graphdraw_code_blocks` option (`Options::CODE_BLOCKS`) and off by default.
    - `Elementor/`: the Mermaid Diagram widget of Elementor (3.5 and later). `Registrar` registers it with Elementor, and the `graphdraw-elementor` script, on Elementor's own actions, and loads `graphdraw-elementor-editor` into Elementor's editor when the renderer doesn't offer every theme. `DiagramWidget` is the widget, a subclass of Elementor's `Widget_Base`: the block's settings as controls, named as the block's attributes, which it outputs through `Diagram::render()`.
  - `Admin/`: what only the admin needs.
    - `SettingsPage`: the settings page, Settings > GraphDraw. It has the theme of diagrams that have none of their own, and a switch for each optional part of the plugin, which it lists itself. Other code adds a switch with `add_switch()` on the `graphdraw_register_settings` action, and reads it with `Options::is_on()`.
    - `Editor`: loads the site's renderer into the editor iframe and the block's editor script, and tells the editor the themes offered with the site's renderer, the theme each other one is shown as, the site's theme, whether to draw the saved images, the URL of the math module, the site's icon packs, and, with Pele, the site's options for it.
  - `Images/`: the saved images of diagrams.
    - `SavedImages`: the saved images of diagrams, for readers that run no JavaScript. PNG files in `uploads/graphdraw/`, listed for each post in its `_graphdraw_images` meta by a key: the hash of a diagram's code and theme, and, for Pele, of the renderer. It checks and saves an image, finds the one of a diagram, and deletes those of a deleted post. A switch on the settings page, stored in the `graphdraw_save_images` option (`Options::SAVE_IMAGES`) and off by default.
    - `ImageSync`: keeps the saved images of a post in step with its diagrams. It tells which diagrams of a post lack an image, and removes the images of the diagrams a post no longer has when the post is saved.
    - `ImagesController`: the REST routes, `graphdraw/v1/posts/<id>/images`, which tell the block editor which diagrams to draw and take the images.
  - `Posts/`: the posts diagrams are in.
    - `PostDiagrams`: the diagrams in the content of posts. It finds them by index, creates diagram blocks, and adds, replaces and removes them.
    - `EditablePosts`: finds the post a request names, and tells whether the current user may work with its diagrams. The abilities and the REST routes share it.
  - `Abilities/`: the abilities of the WordPress Abilities API (WordPress 6.9+), one class per ability. `Ability` is the abstract base: a subclass defines the name, texts, schemas, annotations, permission check and execute callback, and `get_args()` puts them together for `wp_register_ability()`. `DiagramAbility` is the base of the abilities that work on diagrams, and `PostAbility` of those that work on a diagram of one post: it finds the post, checks the permission, and leaves `run()` to the subclass. `Schemas` has the parts of a schema they share. `Registrar` lists the classes of the abilities, and registers them and their `graphdraw` category. `ClientAbilities` loads the client-side abilities in the block editor.
- `src/abilities/`: the abilities that run in the browser, a script module (WordPress 7.0+): `graphdraw/validate-diagram` parses a diagram with the editor's renderer, and names its type as Mermaid.js does (`flowchart-v2`, `classDiagram`, `stateDiagram`). The server can't parse Mermaid.
- `src/block.json`: block metadata. It refers to the shared assets by handle.
- `src/edit.js`, `src/components/`: editor UI. `edit.js` has the preview, the caption, the code field, shown while the block is selected and under the preview, and a toolbar menu that downloads the preview or copies it as a PNG. `code-input.js` is the code field (line numbers, Tab indentation, the marked error line, a link to Mermaid's syntax in its help), `mermaid-diagram.js` the live preview (with Pele, drawn again when web fonts finish loading and when its width changes), and `diagram-settings.js` the sidebar: the theme, the toggles for the visitors' controls, and the accessible title and description.
- `src/editor/settings.js`: what the server tells the editor about themes (`Admin\Editor`): the labels of those offered with the site's renderer, the theme each other one is shown as, the site's theme, the URL of the settings page, the URL of the math module, the site's icon packs, and, with Pele, the site's options for it.
- `src/editor/saved-images.js`: draws the saved images. When a post is opened in the editor, and each time it is saved, it asks the routes of `ImagesController` which diagrams lack an image, draws each as a PNG with the renderer of the editor canvas, and sends it.
- `src/renderers/`: a renderer draws and parses diagrams behind one interface: `draw( code, theme, element, id )` resolves to `{ svg }` or `{ error: { message, line } }`, and `parse( code )` to `{ type }` or the same error (built by `error.js`); neither throws. `getStyle( code, theme, element )` returns the CSS properties for the element that holds the SVG, Pele's palette, or null for Mermaid.js. `mermaid.js` wraps Mermaid.js in it, `pele.js` Pele, and `getRenderer()` in `index.js` returns the renderer of a given window. The Pele renderer also has `forgetTextWidths()`, for web fonts that loaded, and `enableZoom()`, Pele's zoom, for the controls, which import no Pele. `createPeleRenderer()` is the one place Pele's options are built, for the front end (`load-renderer.js`) and the editor (`index.js`), and is given the loader of the math module (`loadMath`).
- `src/utils/`: `toSourceLine()` maps Mermaid's error lines back to the source, `getIndentEdit()` works out what Tab and Shift+Tab change, `export-diagram.js` turns a rendered diagram into an SVG or PNG file, and `mermaid-config.js` is the shared config, with the diagram types it lays out with dagre. For themes: `themes.js` lists them, and turns the theme a diagram asks for into what it is drawn in (`resolveTheme()`) and into Mermaid configuration (`getThemeConfig()`), and reads the one the code asks for (`getCodeTheme()`); `pele-palette.js` has the palettes of Pele; `getSurface()` tells whether an element sits on something dark; `watchSurface()` tells when that may have changed. `watchFonts()` tells when web fonts finish loading, and `watchWidth()` when the content width of an element (`getContentWidth()`) changes. `redrawn-event.js` names the event a diagram gets when it was drawn again in place. `full-layout.js` draws a Pele diagram in full for the files made from it. `accessible-text.js` writes a title and a description into a rendered SVG, and reads them back (`getAccessibleText()`) for another drawing of it.
- `jest.config.js`: the default configuration of `wp-scripts`, and Babel for Pele (an ES module package), so tests draw with the real one. jsdom has no canvas, so they give it a text measurer.
- `src/view.js`, `src/frontend/`: front-end rendering, for every integration. Each diagram renders when it scrolls into view, and `load-renderer.js` loads the renderer the page names (with `load-mermaid.js` for Mermaid.js, and by importing `build/pele/lazy.js` for Pele) when the first one does. `controls.js` then adds the buttons the diagram asks for, `zoom.js` zooms and pans a Mermaid.js diagram (a Pele diagram gets Pele's own zoom instead, through the renderer's `enableZoom()`), and `fullscreen.js` shows it over the whole screen: those three are a file of their own, `build/controls.js`, which `load-controls.js` loads for the first diagram that asks for a control. A diagram that follows the page is drawn again when the page turns dark or light, and a Pele diagram when it changes width (`redraw-on-resize.js`). `view.js` and `controls.js` are explicit entries in `webpack.config.js`: `block.json` refers to the first by handle, and nothing but a URL refers to the second.
- `src/frontend/math.js`: the math module, `typeset( tex, size, doc )`, which wraps Temml: it returns `{ html, width, height }`, Temml's MathML measured in a hidden element in `doc`, or null when Temml can't parse the TeX. `src/utils/load-math.js` imports it by URL (`mathUrl` in `graphDrawSettings` and in the editor's settings; a page cached before that names no URL, so it is looked for next to Pele). An entry of the module half of the build, `build/math.js`. Pele diagrams only.
- `src/utils/icons.js`: icons from the packs of `IconPacks`, with no icon of its own. `parseIconName()` maps a name as a diagram writes it to a pack and an icon (`fa:fa-car` to `fa` / `car`, `fab:fa-github` to `fab` / `github`, `fa:user` and `logos:aws` as they are), `getIconSvg()` builds the SVG from an Iconify pack's `body`, `width`, `height`, `left` and `top`, `loadPack()` fetches a pack's JSON once per page, and `createIcons()` gives a Pele renderer the icons whose packs are loaded. `registerIconPacks()` in `src/renderers/mermaid.js` hands the packs to Mermaid.js.
- `src/elementor.js`: the script of the Elementor widget. Elementor renders a widget again after each change in its editor, and shows some after the page loaded, as in a popup: on Elementor's `frontend/element_ready` hook of the widget, it calls `window.graphDraw.render()` for it. An entry of its own in `webpack.config.js`, which the widget declares, so only pages with the widget load it.
- `src/elementor-editor.js`: the script of Elementor's editor, which `Elementor\Registrar` loads there only when the renderer doesn't offer every theme. When Elementor opens the section of a Mermaid Diagram widget's theme, it shows a theme that isn't offered as the one it is drawn as: Elementor's select shows nothing for a value it has no option for. An entry of its own in `webpack.config.js`.
- `src/save.js` returns `null` because the block is dynamic. `src/deprecated.js` migrates older saved markup.
- `src/transforms.js`: turns selected blocks holding a fenced `mermaid` code block (for example, pasted from Obsidian) into a diagram block, and a Code block with the `language-mermaid` class too.
- `tests/`: the PHPUnit tests, with WordPress from Composer (`vendor/roots/wordpress-no-content/`) and its test library (`wp-phpunit/wp-phpunit`). Those of the Elementor widget are in `tests/Elementor/`, with Elementor from Composer too (`vendor/wordpress-plugin/elementor/`).
- `build/`: generated by `npm run build`. `vendor/`: generated by `composer install`. Neither is committed.
- `.wordpress-org/`: plugin directory banners, icons and screenshots. Not part of the zip.

## Invariants

None of these is obvious from the code, and each has broken before.

- **The editor canvas is an iframe.** Previews must render with the copy of the site's renderer loaded in that iframe, found with `getRenderer( element.ownerDocument.defaultView )`. Rendering in the parent window measures labels against the wrong CSS. Don't import `mermaid` or `pele` into the editor bundle: they are the separate `mermaid-js` script (`build/mermaid.min.js`) and `pele-js` script (`build/pele.global.js`), registered in `includes/Assets.php`. `Admin\Editor` loads the chosen one, and only that one, into the canvas (`enqueue_canvas_assets()`) and into the admin window, for editors that are not iframed (`add_renderer_to_block()`, which puts it in the block's editor script handles): `block.json` therefore lists no library as a dependency of the block's editor script. With Pele the editor loads no Mermaid.js at all, and `getRenderer()` finds the library by its global, `window.pele` or `window.mermaid`.
- **The front end loads Mermaid on demand.** `load-mermaid.js` imports Mermaid's ES module build (`build/mermaid/`) by URL at runtime, so it's never bundled, and the build loads each diagram type's code on first use. Don't make the `graphdraw-diagram` script depend on `mermaid-js`. `webpack.config.js` copies the build with `.mjs` renamed to `.js`, because not every server serves `.mjs` as JavaScript, and fails if an import it can't rewrite is left.
- **A page loads one renderer, never both.** The site's renderer, Mermaid.js or Pele, draws every diagram of a page, and `graphDrawSettings.renderer` names it. A page cached before the setting existed names none and gets Mermaid.js. Pele's lazy build (`build/pele/`: the entry, `core.js`, and the code of each diagram type) is imported by URL like Mermaid's, so it is never bundled, and a diagram loads the code of its own type only; the build copies it as it is, and fails if a file imports another by anything but a relative `.js` path. The editor loads Pele's single-file build (`build/pele.global.js`) instead of Mermaid.js, never both. The settings are told when the page's scripts are enqueued, not when the script is registered: a `graphdraw_renderer` filter that looks at the page, such as `is_page()`, can't answer earlier.
- **A page loads what its diagrams use, and no more.** What a page with a diagram loads is `build/view.js`, then Mermaid's core and the code of the diagram's type when the diagram scrolls into view, and the controls only for a diagram that has some. `view.js` must not import `controls.js`, `zoom.js`, `fullscreen.js` or `export-diagram.js`: they are the module `build/controls.js`, imported by its URL like Mermaid, so no optimisation plugin's handling of scripts gets in the way. A page cached before that file existed names no URL for it, so `view.js` then looks for it next to Mermaid. Measure a change to what the front end loads in a browser, per diagram type, before and after (#28).
- **ELK is loaded only for a diagram that needs it.** Mermaid 12 lays out flowcharts, class, state, ER, requirement, use case and agent flow diagrams with ELK unless told otherwise, and ELK is 1.6 MB of JavaScript: twice everything else a flowchart loads. `mermaid-config.js` gives those types dagre, the layout they had before Mermaid 12, each by its own options (`DAGRE_TYPES`). Not with `layout` for all types: mind maps and swimlane diagrams have layouts of their own, which that would replace. Use case diagrams, new in Mermaid 12, keep ELK (`ELK_TYPES`): dagre draws the lines between use cases through other use cases. Look at a type with a diagram of a dozen links before moving it to dagre. A diagram that names a layout in its front matter or in a directive, such as `layout: elk`, gets it, because the code decides before the site does. The old `flowchart-elk` keyword no longer selects ELK in Mermaid 12, so the Mermaid.js renderer does that for it. `src/utils/test/mermaid-config.js` compares the two lists with the bundled Mermaid.
- **One Mermaid config.** The editor and the front end share `src/utils/mermaid-config.js`, so the preview matches the published diagram. It has options per diagram type, and so has the configuration of a theme: put the two together with `mergeConfig()`, never by spreading, which would drop one of them. Don't set `htmlLabels: false`: SVG text labels show `&amp;` literally and drop `>` (#7).
- **The escaping in `Diagram::get_source_markup()` is deliberate.** `esc_textarea()` round-trips the source exactly, and `[` and `]` become `&#91;` and `&#93;` so `do_shortcode()` doesn't expand diagram text such as `A[gallery]`. Don't switch to `esc_html()` or drop the bracket encoding. The wrapper's attributes get the same encoding (`Diagram::encode_brackets()`): `do_shortcode()` also expands shortcodes inside attribute values, such as an accessible title.
- **A shortcode gets its content after the content filters.** `wpautop()` has ended each line with `<br />` and wrapped what blank lines separate in `<p>`, and the editors and kses store `>`, `<` and `&` as entities. `Shortcode::get_code()` undoes exactly that, and keeps a `<br>` in the middle of a line, which is a line break in a label. Those filters, and `do_shortcode()` itself, also take everything from a `<` to the next `>` for a tag: a class diagram ending with `Animal <|-- Duck` would hide the shortcode's closing tag in one. So `Shortcode::protect_code()` runs before them, on the filters that run shortcodes in content, and writes the `<` and `>` of the code as entities. Code passed straight to `do_shortcode()`, as some page builders do, doesn't get that: there a `<` needs a `>` after it, or has to be written as `&lt;`. `wptexturize()` is kept away with `no_texturize_shortcodes`, only for the tags that are the plugin's at that moment: `[mermaid]` is registered late and only when it is free, so another plugin that has it keeps it.
- **Code shown as a diagram is read as a browser shows it.** `CodeBlocks::get_code()` walks the `<pre>` element with the HTML Tag Processor and takes its text. A `<` that starts no tag, as in `Animal <|-- Duck`, is text, where `strip_tags()` would cut the code off; character references are decoded; the elements a syntax highlighter added are dropped and their text kept; a `<br>` element stays a `<br/>`, a line break in a label. The class is matched on the `<pre>`, or on the `<code>` that opens it, never in the text. `getCode()` in `src/transforms.js` reads a Code block the same way. The element is replaced on the server, so a script that looks for `language-mermaid` in the page finds nothing to draw a second time. In content the filter runs at priority 10: after `wpautop()` and `wptexturize()`, which leave a `<pre>` alone, and before `do_shortcode()`, which would expand a node such as `A[gallery]`. The setting is read only once the class was found as text, so a page without such code never reads it.
- **Saved markup is versioned.** When the output of `save.js` or the block's attributes change, add an entry to `deprecated.js` with a test. Without one, existing posts show "This block contains unexpected or invalid content".
- **The transform is asked about every block.** `src/transforms.js` registers it for `*`, so `isMatch` gets the attributes of whatever is selected: blocks with no `content`, or with something other than text in it. An exception there takes the whole editor down when the Transform menu opens (#6).
- **A theme is set per render, and renders take turns.** Mermaid has one configuration per window and no theme per render. The Mermaid.js renderer's `draw()` initialises Mermaid again when a render needs another configuration than the last one had, which is another theme, or ELK for a `flowchart-elk` diagram, and queues the renders of each Mermaid instance, because Mermaid reads its configuration all through a render. Don't call `mermaid.initialize()` or `mermaid.render()` anywhere else once diagrams render.
- **The themes are listed twice.** `Themes::get_all()` in `includes/Themes.php` has their names and labels, which the settings page and the editor show, and `THEMES` in `src/utils/themes.js` has the names for the front end. Both list every theme of the bundled Mermaid, except `null`, which only removes a diagram's colours. `src/utils/test/themes.js` compares the two lists with each other and with Mermaid's. So are the dark themes: `Themes::DARK`, and `isDarkTheme()` in `src/utils/themes.js`, which the same test compares.
- **Automatic is not Mermaid's `default` theme.** Given no theme, Mermaid 12 picks one per diagram type: `redux-color` for flowcharts, sequence, class, state and ER diagrams and a few more, `default` for the rest. `auto-light` names no theme, so diagrams look as they did before they could have one. `auto-dark` names the dark counterpart of each of those picks, read from `mermaidAPI.defaultConfig` (`getThemeConfig()`). Naming `default` gives every type the classic look instead.
- **A diagram that follows the page reads its surface, not the system.** `getSurface()` looks for the nearest background colour behind the diagram, and falls back to the colour of the text. `prefers-color-scheme` alone says nothing about a page: most themes are light whatever the system is. The block editor gives a block around a diagram its colours only after the preview first rendered, so `mermaid-diagram.js` watches the elements around the preview and draws again.
- **A theme that isn't offered is kept, and shown as the one it is drawn as.** Pele draws a theme as light or dark, so with Pele the settings page, the block's sidebar and the Elementor widget offer Automatic, Light and Dark (`Themes::get_offered()`), which are stored as `auto`, `default` and `dark`. A diagram, or the site, may have another theme from before the site switched renderer: it is never rewritten, so it looks the same with Pele and gets its own look back if the site switches back. A picker shows it as Light or Dark (`Themes::get_aliases()`, `getShownTheme()`), and it changes only when someone picks another theme: the settings page's option for it submits the stored theme, the block's attribute is set only on a change, and `src/elementor-editor.js` changes the select of Elementor's panel, never the widget's settings. `exists()` and `resolve()` still take every theme, so what a diagram is drawn in doesn't depend on what is offered. The abilities take every theme too, so attributes an ability returned can be passed back as they are; with Pele, `Abilities\Schemas` says which three mean something, and that colours in the code are ignored.
- **A theme maps to a palette with Pele.** Pele has no named themes: it draws with `--pele-*` CSS variables, light by default. `getPaletteName()` in `src/utils/pele-palette.js` says which of the two palettes a diagram gets: `auto-dark` and the dark themes (`isDarkTheme()`, which Mermaid.js's dark counterparts share) are dark, `auto-light` and every other theme light, and a theme written in the code (`getCodeTheme()`: front matter `config.theme`, or `theme` in an `%%{init}%%` directive, a directive winning) wins over the block's. `themeVariables` and other colours in the code are ignored. The palette is put on the canvas as variables, by the Pele renderer's `getStyle()`, never written into the SVG: when the page turns dark or light, `redrawDiagram()` gives a diagram whose renderer has a style the other palette in place, with no new drawing and its controls kept, where Mermaid.js diagrams are drawn again. `--pele-bg`, which fills the boxes behind edge labels and the gaps between pie slices, takes the colour of the surface under the diagram when `getSurface()` reads one that is as dark or light as the palette, so a dark diagram on a light page isn't given a light background. The dark palette's contrast is tested; look at a change to either palette on a dark and on a light page, with a pie chart and a Gantt chart, whose series colours are the ones that fade first.
- **Every SVG has the id of its drawing.** The ids of the accessible title and description are made from the SVG's id (`setAccessibleText()`), so two diagrams on a page that share none would have `aria-labelledby` point at the first one's title. Mermaid.js gives its SVG the id it was asked to draw with, and the Pele renderer writes it in.
- **A renderer's `draw()` and `parse()` never throw.** `draw()` returns `{ svg }` or `{ error: { message, line } }`, and removes the elements Mermaid leaves in the document after a failed render. Callers rely on that contract. Reach Mermaid only through a renderer.
- **Error lines are lines of the source, not Mermaid's.** Mermaid removes the front matter, directives, comment lines and leading blank lines before parsing, and numbers the lines that are left. `toSourceLine()` applies the same removals to map a line back, so it mirrors `preprocessDiagram()` of the pinned Mermaid version. Mermaid's own "Parse error on line N" is dropped from the message for the same reason.
- **The code is saved as it is typed.** `edit.js` sets the `code` attribute on every change, and only the preview waits for typing to pause (`PREVIEW_DELAY`). When the attribute waited too, a save right after typing left the last characters out.
- **The code field shows while the block is selected**, and also when the block has no code or the code has an error, so what needs fixing is always in sight. It comes after the preview, so the diagram that was clicked doesn't move.
- **Tab in the code field must not trap the keyboard.** Tab and Shift+Tab indent and outdent, and Escape lets the next Tab move focus; the field's help text says so. The handler runs in the capture phase, because the block editor's own Tab handler, on an ancestor, moves focus out of the block unless the key is already handled.
- **Zooming is scrolling.** A zoomed Mermaid.js diagram is an SVG wider than its canvas, and the canvas scrolls, so panning by touch, trackpad, scrollbar and arrow keys is the browser's own. `zoom.js` only adds dragging with a mouse, and zooming with Ctrl or Cmd and the wheel. The wheel alone must always scroll the page.
  A Pele diagram with the zoom control gets Pele's zoom instead (`enableZoom( canvas, { always: true, labels } )`, from the renderer, so `controls.js` imports no Pele and nothing new loads): pinch, Ctrl or Cmd and the wheel, drag, double-click, `+` `-` `0` and arrow keys, and Pele's buttons in the canvas, in place of the plugin's. Pele's zoom works on the SVG that is the canvas's first child and sets the SVG's `viewBox` and style, and it ignores a wheel without Ctrl or Cmd. `redrawInPlace()` dispatches `REDRAWN_EVENT` (`src/utils/redrawn-event.js`) on the diagram after the new drawing is in, and `controls.js` listens for it and calls `zoom.refresh()`, which reads the new SVG and resets the zoom to fit, as Pele's zoom does by itself when its canvas changes size: `view.js` and `controls.js` are bundles of their own and share no module state. The zoom is kept per canvas, so a canvas that takes the place of another gets one of its own. Fullscreen resets either zoom.
- **Fullscreen has a fallback, and survives a redraw.** Where the browser shows no element fullscreen, as on an iPhone, or refuses to, `fullscreen.js` makes the diagram an overlay over the page instead, stops the page behind it from scrolling, and closes it on Escape. The page is no longer behind a fullscreen diagram, so it gets the colour of what it sat on (`getSurface()`) as its background: without one, a diagram drawn for a dark page would sit on the browser's white. The state is kept per diagram, not per toolbar, because a diagram that is drawn again gets new controls. Going in or out resets the zoom, which is relative to the size the diagram had.
- **Pele's options come from one place, and the plugin's own win.** The site's options (`PeleOptions`, told as `peleOptions` by `RendererSettings`, to the front end and the editor) are merged under `idPrefix`, `responsive`, `fontFamily`, `fontFamilyMono` and `measurer` in `createPeleRenderer()`; `maxWidth` is the plugin's too, so a site can't set it. `autoDirection` is not set, so Pele's default holds (on, below 640 px) unless the site's options say otherwise. Don't read Pele's options anywhere else, and never let a diagram's author set them: links, images and limits are the site's decision (Pele's security page). The filter is read on every request that prints the settings, so it must stay cheap.
- **Pele is drawn again when web fonts load.** Pele measures labels in the font the browser has at that moment. The font comes from `--pele-font` on the diagram's element, else its computed `font-family`, and the monospace font from `--pele-font-mono`, else `monospace`. When `document.fonts` fires `loadingdone`, the front end (`view.js`, once per page, only with Pele) and each editor preview (in the canvas document) call `forgetTextWidths()` and draw again. `redrawInPlace()` in `render-diagrams.js` changes only the SVG element of a rendered diagram that has a renderer style (Pele): the canvas keeps its palette, and the diagram its toolbar, zoom and the element the zoom holds. Mermaid.js diagrams are left alone. `document.fonts` may be missing (jsdom): `watchFonts()` then does nothing.
- **Pele diagrams are laid out for their width, and drawn again when it changes.** The Pele renderer's `draw()` passes the content width of the `element` it is given (`getContentWidth()`: width less horizontal padding) as `maxWidth`, so Pele may turn a wide diagram vertical on a narrow screen. An element with no width, one that is hidden or off the page, gets none: the full layout. A `ResizeObserver` on the element the diagram is laid out for (`watchWidth()`, in the window of the element, so in the editor canvas iframe too) draws a Pele diagram again, at most once a frame, only when the content width is not the one it was last drawn for: drawing changes the height, which must not loop. On the front end `redrawOnResize()` watches the diagram element, which `draw()` measures and fullscreen enlarges (a theme may pad it and not the canvas), and draws with `redrawInPlace()` (the canvas, toolbar and palette stay), in the editor `MermaidDiagram` draws again. Fullscreen in and out, a resized window and a rotated phone all go through the observer. Mermaid.js diagrams are never observed. The width is read from the page, so a diagram rendered while hidden is drawn again when it is shown.
- **Exports of a Pele diagram are drawn again in full, not taken from the page.** The SVG on the page has the layout of the screen it is on; a file, a copied image or a saved image must not depend on that. Download as SVG and Download as PNG (the front end's `controls.js` and the editor's toolbar menu) and the editor's Copy as PNG go through `withFullLayout()` in `full-layout.js`, which draws the diagram for a hidden element inside the canvas: no width, so no `maxWidth`, and the fonts and `--pele-*` variables of the diagram are inherited, which `getSvgMarkup()` then writes into the file. Saved images draw for a hidden element in the editor canvas's body, for the same reason (the body has a width). `controls.js` has no renderer of its own and must not import one: `view.js` hands it the renderer that drew the diagram, already loaded. Mermaid.js exports are the SVG on the page, as before.
- **A Pele file gets its colours written in.** A Pele SVG draws with `var(--pele-*)` and the font with `var(--pele-font)`, which a page supplies and a file doesn't have: an SVG file or a PNG drawn from it would be black on transparent, or the light fallbacks on a dark diagram. `getSvgMarkup()` writes the values the diagram has on the page (computed on it, so a stylesheet of the site counts too) in place of every `var()`, and leaves no variable behind; Download as SVG, Download as PNG, Copy as PNG and the saved images all go through it. A PNG's background is `--pele-bg`, which is the surface's colour or the palette's, as the label boxes have it: not a white or a dark guess from the surface alone, which would give a dark diagram on a light page a white background. A diagram that isn't on a page, as a saved image, has the values on its own style.
- **A site restyles Pele diagrams with Pele's CSS variables and classes.** Pele's SVG has nothing in common with Mermaid.js's, so CSS written for one doesn't apply to the other. The palette is set inline on the canvas (`getStyle()`), so a site's own colour variables must go on the SVG inside it to win. The fonts are read on the diagram element (`--pele-font`, `--pele-font-mono`), measured in and written into the SVG, so they go on the diagram, not on the SVG. The readme's "Styling Pele diagrams with CSS" tells sites so: change it when the plugin changes where it sets them.
- **The copy button needs a clipboard.** `navigator.clipboard` exists only on pages served over HTTPS (and on localhost), so elsewhere the button is left out rather than shown and failing. The editor's Copy as PNG also needs `ClipboardItem` (`canCopyImage()`), and is left out the same way. `copyDiagram()` gives the clipboard the PNG as a promise, so the write starts while the click still counts: Safari refuses one that starts after the PNG has been drawn.
- **A downloaded diagram states its own size.** On the page, a diagram's size follows the page's width and the zoom. `getSvgMarkup()` gives the file the size of the `viewBox` instead. The PNG is drawn from that SVG in a `data:` URL: from a `blob:` URL, Chromium refuses to read back a canvas that an SVG with HTML labels was drawn on.
- **The front-end script has no dependencies**, not even `wp-i18n`. The labels of its buttons are translated in `includes/Assets.php` and passed in `graphDrawSettings`.
- **`build/` and `vendor/` are generated, and only releases ship them.** A copy of the repository can't run until `composer install` and `npm run build` ran: `graphdraw-mermaid-diagrams-flowcharts.php` checks for both and shows a notice instead of loading. The Playground blueprint (`blueprint.json`) installs the zip attached to the latest GitHub release, so each release needs `graphdraw-mermaid-diagrams-flowcharts.zip` attached. Never edit `build/` by hand.
- **The release zip gets the production autoloader.** `npm run plugin-zip` installs Composer's packages without development dependencies before it zips `vendor/`, then installs them again. Zipping `vendor/` any other way ships PHPCS.
- **Classes are autoloaded, so a class's file is named after it.** Composer maps `GraphDraw\` to `includes/`. A new class needs no `require`, but its file name must match the class name, and its folder the namespace, case included: macOS doesn't mind a mismatch, Linux servers do. `includes/functions.php` holds the only global function, `graphdraw()`, and `graphdraw-mermaid-diagrams-flowcharts.php` requires it.
- **A request loads only the classes it needs.** `Plugin` creates nothing but the parts in its lists, and the container creates what those ask for in their constructors. So a class that a front-end part asks for loads on every page view: don't give `Block`, `Diagram`, `Shortcode` or `CodeBlocks` a constructor parameter from `Admin/`, `Abilities/` or `Posts/`. `tests/PluginTest.php` names what a front-end request creates. Whether a part is needed is decided by the request, never by the switch of its feature: `SavedImages` still deletes the images of a deleted post after the setting was switched off.
- **A part that waits for an action is added each time it fires.** `Plugin::add_deferred_hooks()` runs at priority 0 of each action in `DEFERRED_PARTS` and calls `hooks()` of the parts that wait for it, so the callbacks of the part, at the default priority, run in that same firing. A part lists every action it hooks into that can come first. `hooks()` only adds hooks, and may run more than once. A hook of such a part can't be removed before its action: remove `array( graphdraw(), 'add_deferred_hooks' )` from the action instead.
- **The Elementor widget loads only with Elementor.** `DiagramWidget` extends Elementor's `Widget_Base`, so loading it anywhere else is a fatal error: only `Registrar::register_widget()`, on Elementor's `elementor/widgets/register` action, names it. So `tests/PluginClasses.php` leaves it out where Elementor isn't loaded, the zip check in CI gives it a stand-in parent, and the container never creates it: Elementor does, with arrays for its constructor. It is the one class of the plugin that reaches the others through `graphdraw()`. Its tests run with Elementor active, the others without, because Elementor changes what WordPress outputs, such as the attributes of images in content. Elementor is pinned to an exact version in `composer.json`, the zip from WordPress.org with its checksum.
- **Elementor keeps the controls of a widget only in its editor.** On the front end, `get_controls()` returns little more than their types and defaults, and Elementor builds them once per request either way. `DiagramWidget::register_controls()` runs on the front end too, so it reads nothing of `Admin/` there: the link to the settings page is added only in the admin. Its tests build the controls as the editor gets them.
- **The constructor of a part asks for objects only.** The container reads the types of the parameters, so a string or an array there can't be created. `Files` is the one object made by hand, from the plugin's main file, in `Plugin`'s constructor. `tests/ContainerTest.php` creates every class, and fails for a parameter that is no class and for two classes that need each other.
- **A diagram in a post is addressed by its index and its hash.** Blocks have no ids. The index counts the diagram blocks of a post in document order, nested ones included, from 0, and the hash is the MD5 of the serialized block. `PostDiagrams` refuses a change whose hash doesn't match (409), so an edit made in the meantime, or another diagram moving to that index, is never overwritten. Removing a nested block also removes its `null` from the parent's `innerContent`, or the parent no longer serializes.
- **Writes go through `wp_update_post()`, after `wp_save_post_revision()`.** WordPress saves a revision of what a post becomes, so a post that was never updated has no revision of what it was. Saving one first makes every change by an ability undoable from the revisions screen.
- **The abilities' permissions are the editor's.** A user works with the diagrams of the posts they may edit (`edit_post`): contributors their drafts, authors their own posts, editors and administrators all, subscribers and visitors none. Reading needs the same, because it returns the source. Only post types edited in the block editor are reached, and not posts in the trash.
- **Read-only abilities run over GET.** The REST API picks the method from the annotations: GET for `readonly`, DELETE for `destructive` and `idempotent`, POST otherwise. An ability that changes its annotations changes how clients call it.
- **The client-side abilities are a script module.** `@wordpress/abilities` exists only as a module, so `src/abilities/` is built by the module half of `wp-scripts build --experimental-modules`, and `webpack.config.js` tells it to import the two WordPress modules rather than bundle them. The controls of diagrams are built by the same half, because a file the browser imports by URL has to be a module. A module can't read translations: `ClientAbilities` passes its texts as script module data. With the flag, wp-scripts no longer empties `build/`, so `npm run build` does it first (`prebuild`).
- **The variations come from PHP.** `Block` registers them with a `variation_callback` from `DiagramTypes`, so the editor and the `list-diagram-types` ability show the same starter code. Don't add variations in JavaScript.
- **The attributes are listed twice.** `src/block.json` defines them, and `PostDiagrams::ATTRIBUTES` lists those the abilities may set, with their types. A new attribute needs both, and its description in `Abilities\Schemas`, which makes the schema of the abilities from that list. `tests/PostDiagramsTest.php` compares the two lists, and `tests/SchemasTest.php` tells when a description is missing.
- **A saved image is found by its key, not kept up to date.** `SavedImages::get_key()` hashes the code and the theme a diagram block has, and, for Pele, the renderer: Mermaid.js's key is what it was before there was a choice, so the images made then keep working. An image's file name and its entry in the meta name a Pele image as Pele's. `Block::render()` looks that key up in the meta of the post being shown, so a diagram that changed, in the editor or through an ability, finds nothing (but the other renderer's image, a stand-in: see below) and outputs its source as before: nothing has to notice the change for an outdated image to stop being shown. `ImageSync::prune()` deletes the file when the post is saved. The site's theme is not part of the key. When it changes, the diagrams that take it keep their images, and `ImageSync::get_missing()` lists them to be drawn again.
- **The other renderer's image stands in until the diagram is drawn again.** After the site switched renderer, `SavedImages::find_key()` looks for the image of the request's renderer, then for the other's, so a feed or a browser without JavaScript shows a picture in the old look rather than the code. `ImageSync::get_missing()` lists a diagram as missing until it has an image of the current renderer, which opening the post in the editor draws. `ImageSync::prune()` keeps the image `find_key()` gives each diagram, so the other renderer's only while the diagram has none of the current one, so a save before the drawing is done doesn't leave the diagram with no image at all. With a filter that picks the renderer per request, a post's editor and its pages can get different renderers: the stand-in covers that, and each save keeps the images of the renderer it runs with.
- **The editor says which renderer it draws images with.** The server can't know: a `graphdraw_renderer` filter that looks at the request may give the REST routes another renderer than the editor canvas loaded. `saveImages()` asks which diagrams lack an image, and sends each image, with `?renderer=<name of the canvas's renderer>`, and the routes key and label the images by it. Without the parameter, the request's renderer is used.
- **Only the editor can draw an image, and the server says which.** `src/editor/saved-images.js` asks for the diagrams of the saved post that lack an image and draws those, from the saved code, never from the blocks being edited: an image is of what readers get. The route takes an image only for a key the post has at that moment. The diagrams are those `PostDiagrams` finds in the post's content, so one in a synced pattern or a template part gets no image, and neither does a shortcode.
- **A saved image is a PNG file named by the server.** What the editor sends is checked as a PNG, by its signature, by `getimagesizefromstring()` and by its size, and written as `<post>-<key>-<theme>.png`, so nothing that was uploaded is ever output as markup or run. `SavedImages::get_all()` reads the meta as something an import could have written: an entry whose file isn't a PNG directly in the plugin's directory is ignored, so no other file is shown or deleted. Not an SVG: its HTML labels would need sanitising, and feed readers and mail clients drop it.
- **A saved image costs nothing where scripts run.** It is output in a `<noscript>` element, so those browsers never fetch it, and `SavedImages::find()` reads the post's meta, which came with the post, before the option. `@media (scripting: none)` hides the source next to the image; a browser without that media feature shows both. In a feed the image takes the place of the source (`SavedImages::replaces_source()`).
- **The editor canvas must have loaded before an image is drawn in it.** The scripts of the canvas run before its document has a body, and Mermaid draws in the body. `findCanvasMermaid()` waits for the document to be complete: without that, the images of a post opened from a warm cache fail to draw.
- **Math loads only for a diagram that has `$$`, and is measured in the diagram's document.** `createPeleRenderer()` is given `loadMath`, and calls it, once, before drawing code that contains `$$`; then Pele gets a `math` resolver, `( tex, size ) => typeset( tex, size, element.ownerDocument )`, which wins over the site's. In the editor that document is the canvas iframe, where the browser lays the MathML out with the fonts and CSS the preview has. Code without `$$` never loads `build/math.js`, and a page without math requests nothing of Temml. If the module can't be loaded, the error is logged and the diagram is drawn without math: the label shows its TeX, as Pele does with no resolver. Temml writes MathML, so no Temml fonts or CSS ship. Mermaid.js diagrams have their own KaTeX and don't use this.
- **Icon markup comes from the packs a site registered, and nothing else.** A pack is fetched only for a diagram that names one of its icons, and once per page (`loadPack()` caches by URL, a failure too, logged once). A name a diagram writes only picks an icon: it is never written into markup, and a name that isn't in a loaded pack gets nothing, so Pele keeps its built-in symbol (`database`, `server`, ...) and Mermaid.js its own mark. Both renderers draw icons: Pele calls its synchronous `icons` resolver with the name as written (`fa:fa-car`, `fa:user`, `logos:aws`, and built-in names such as `database`), and `draw()` draws once to note the names, then loads the packs they point at and draws again, only then; the resolver is the plugin's, and wins over the site's. Mermaid.js gets `mermaid.registerIconPacks()` once per instance, with loaders that use the same fetch, on the front end and in the editor canvas (`getRenderer()`); Mermaid calls a loader only for a diagram that uses the pack. Saved images and full-layout downloads draw through the same renderers, so they have the icons.
- **Pele is pinned to an exact version** in `package.json`, and upgraded with Mermaid.js: the release of Pele that follows the Mermaid version the plugin pins (Pele 1.9.0 supports every diagram type of Mermaid 12.1.0), so both draw one syntax. An upgrade of either needs the check of the other. For Pele: its bundle sizes (`build/pele/` and `build/pele.global.js`) and what a page loads per diagram type; that its files still import each other by relative `.js` paths (the build fails if not); that every diagram type draws, in the editor and on the front end, in both palettes; that the variables it reads are the ones `src/utils/pele-palette.js` sets (`grep -o -e '--pele-[a-z0-9-]*' build/pele/chunks/*.js`), and the series colours its charts fall back to; how it numbers the lines of an error against code with front matter, a directive, comment lines and leading blank lines; its error messages, which `src/renderers/pele.js` trims; that `parse()` still names types as Mermaid.js does (`flowchart-v2`, `classDiagram`, `stateDiagram`), for `validate-diagram`; and what it draws differently from Mermaid.js (math, callbacks, links). The plugin also relies on these of Pele's: `maxWidth` and `autoDirection` (a wide `flowchart LR` turns vertical at 375 pixels and not at 1280), `forgetTextWidths()`, `enableZoom()` with `always`, `labels` and `refresh()` (and that it ignores a wheel without Ctrl or Cmd), the `math` resolver (`{ html, width, height }`) and the `icons` resolver (the name as written, such as `fa:fa-car`, and markup it wraps in an SVG of its own), and the CSS variables, classes and `data-id` the readme tells sites to restyle with.
- **Temml is pinned to an exact version** in `package.json` (MIT), for `build/math.js`. An upgrade needs a check of that file's size, that it still parses what labels use (`x^2 + y^2 = z^2`, `\frac{a}{b}`, sums, matrices) and gives null, not an exception, for TeX it can't parse, and its MathML drawn in Chromium and Firefox, in the editor and on the front end, in a downloaded SVG and PNG.
- **Mermaid is pinned to an exact version** in `package.json`. An upgrade needs a check of the bundle sizes (`build/mermaid.min.js` and `build/mermaid/`) and of what a page loads for each diagram type, of security advisories, of every diagram type in both the editor and the front end, of the error line mapping against what the new version removes before parsing, of its themes, and of its layouts: the unit tests fail when it adds a theme, picks one per diagram type that has no dark counterpart in `src/utils/themes.js`, or lays out another diagram type with ELK.
- **The minimum PHP version lives in four places**, which must match: "Requires PHP" in the `graphdraw-mermaid-diagrams-flowcharts.php` header (and `readme.txt`), `testVersion` in `phpcs.xml`, `config.platform.php` in `composer.json`, and the `php-minimum` job in `ci.yml`. Composer resolves the lock for that version, so it installs on every PHP the plugin supports. Without it, a lock made on a newer PHP picks packages CI's PHP can't install.
- **The version lives in four places**, which must match: the `graphdraw-mermaid-diagrams-flowcharts.php` header, "Stable tag" in `readme.txt`, `package.json` and `src/block.json`.

## Reusing diagrams in integrations

The block, the shortcode, the code shown as diagrams and the Elementor widget share their markup and their script, so other editors, such as a page builder widget, can output the same diagrams. An integration whose settings are named as the block's attributes (`code`, `theme`, `zoom`, `download`, `copy`, `fullscreen`, `caption`, `accTitle`, `accDescr`, `align`), as the Elementor widget's are, outputs `graphdraw()->diagram()->render( $settings )`, which does steps 1, 4, 5 and 6, and then needs only steps 2 and 3. The shortcode passes its attributes under those names too. Otherwise, an integration:

1. Outputs `graphdraw()->diagram()->get_markup( $code, $attributes, $caption )`: a `.graphdraw-diagram` wrapper around the escaped source, a `<figure>` when there is a caption. It also enqueues the assets. Check `function_exists( 'graphdraw' )` first: the plugin may be inactive.
2. Declares the `graphdraw-diagram` script and style handles as its dependencies if it renders outside a normal page load, such as over AJAX, where enqueueing has no effect.
3. Calls `window.graphDraw.render( element )` for diagrams added after the page loaded, such as a widget a page builder re-renders in its preview. Each one renders when it scrolls into view. Already rendered diagrams are skipped.
4. Passes `'data-mermaid-controls'`, any of `Diagram::CONTROLS` (`zoom`, `download`, `copy`, `fullscreen`) separated by spaces, in `$attributes` to give visitors those controls. Without the attribute a diagram gets none. `Diagram::get_data_attributes( $controls, $title, $description )` returns this attribute and the two of step 6, for an integration that has the controls as a list and the texts as they were typed.
5. Passes `'data-mermaid-theme'`, a name from `Themes::get_all()`, to draw the diagram in a theme of its own. Without it the diagram gets the site's theme. An integration that builds the wrapper itself, as the block does, gets that theme from `Diagram::get_theme()` and outputs the wrapper with `Diagram::wrap()`; a wrapper without the attribute follows the page.
6. Passes `'data-mermaid-title'` and `'data-mermaid-description'` to give the rendered SVG a title and a description for assistive technology, and the `aligncenter` class to centre a diagram narrower than its column.

The renderer, Mermaid.js or Pele, is the site's setting, and a site's code can pick it per request with the `graphdraw_renderer` filter (`mermaid` or `pele`; anything else is Mermaid.js). An integration needs to do nothing for it: the script draws with whichever the page names, and `window.graphDraw.render()` too.

A site registers icon packs with the `graphdraw_icon_packs` filter (`name => URL of an Iconify JSON file`), for diagrams of either renderer. Icon markup comes from those packs only; an integration needs to do nothing for it.

Page builder previews are iframes, like the block editor canvas: load the assets into the preview and call `render()` from inside it. The Elementor widget does both: it declares the handles, and `src/elementor.js` calls `render()` for each widget Elementor shows.

## Conventions

- WordPress coding standards throughout. The linters are the source of truth.
- Every user-facing string is translatable with the `graphdraw` text domain. ESLint and PHPCS enforce it.
- PHP code lives in classes in `includes/`. A class that adds hooks implements `Hookable`, adds them in `hooks()`, never in its constructor, and is in one of the lists of `Plugin`. A class gets the other objects it needs through its constructor, as parameters typed with their class: the container creates them, and nothing is created with `new` but values.
- JavaScript unit tests live next to the code they cover, in `test/` directories. PHP tests live in `tests/`, one class per class under test, extending `WP_UnitTestCase`.
- A new ability is a class in `includes/Abilities/` extending `Ability`, `DiagramAbility` when it works on diagrams, or `PostAbility` when it works on a diagram of one post, and a line in `Registrar::ABILITIES`.
- Commit subjects start with `FEATURE:`, `FIX:` or `UPDATE:`.

## Workflow

- Branch from `main`. `main` is protected: changes land through a reviewed pull request, and commits must be signed.
- Agents may push feature branches and open draft pull requests that link their issue (`Fixes #N`). Agents never push to `main`, force-push or merge.
- The changelog lives only in `readme.txt` and is written at release time from the merged pull requests. Pull requests don't add changelog entries, and there is no `CHANGELOG.md`.

## Definition of done

- `npm run lint:js`, `npm run lint:css`, `npm run lint:php`, `npm run test:unit` and `npm run test:php` pass.
- Every bug fix comes with a test that fails without it.
- Anything that changes rendering has been checked in the editor and on the front end.
